\section{Method}

We approach clarification as an information-seeking decision problem. 
Given an underspecified task request, the assistant must decide whether to acquire additional information through clarification or proceed with execution based on the currently available specification. 

Our method learns this decision policy from simulated interaction trajectories. 
Each trajectory captures a multi-turn interaction between the assistant and a simulated user, including clarification attempts, user responses, and the final task outcome. 
By evaluating these trajectories, we measure both the task success achieved by the final solution and the interaction cost introduced by clarification.

Using these signals, we construct preference comparisons between alternative interaction trajectories and train the model with preference optimization. This allows the model to learn when clarification improves task success and when direct execution is preferable under different interaction contexts.

Our approach consists of two main components: (1) a reward function that balances task success against interruption cost, and (2) a trajectory generation pipeline with a user simulator that models persona-aware user behaviors. We detail these components in the following subsections.

\subsection{Decision Policy}

We model clarification as a sequential decision process. 
At interaction step $j$, the assistant observes a dialogue state $s_j$, which contains the current task description and interaction context: $s_j = (q_j, u_j, d_j, r_j, p)$, where $q_j$ denotes the current task description (which accumulates conversation history as the dialogue proceeds), $u_j \in [0,1]$ captures the task uncertainty reflecting how incomplete the task specification is, $d_j$ is the current dialogue turn number, $r_j \in \{0,1\}$ indicates whether the previous turn was rejected by the user, and $p$ encodes the user persona.

Based on this state, the assistant selects an action $a_j \in \{\text{Clarify}, \text{Execute}\}$, where \textbf{Clarify} asks the user for additional information and \textbf{Execute} directly produces a task solution.

The assistant follows a decision policy parameterized by $\theta$: $a_j \sim \pi_\theta(a_j \mid s_j)$. During training, we learn this policy from preference comparisons over interaction trajectories. For trajectory generation (before training), we use a heuristic selection function that considers task uncertainty, persona patience, and dialogue history.

An interaction between the assistant and the user produces a trajectory $\tau = (s_1, a_1, s_2, a_2, \dots, s_K, a_K)$, which terminates when the assistant executes the task or when the user ends the interaction.

\subsection{Reward Design}

The reward function is designed to capture the trade-off between task completion success and the cumulative cost of interrupting the user. We decompose the reward into two components: task success reward and interruption cost. The overall objective is to maximize task completion while minimizing user frustration from excessive or ineffective clarification.

\subsubsection{Task Success Reward}

The task success reward $R_{\text{task}}$ measures the functional correctness of the generated solution. This reward is computed only when the assistant selects \textbf{Execute} and generates a solution; for Clarify actions, $R_{\text{task}} = 0.0$ since no solution is produced.

For coding tasks, $R_{\text{task}}$ is measured by executing the generated code against test cases:

\begin{equation}
R_{\text{task}} = \begin{cases}
1.0 & \text{if all tests pass} \\
\frac{n_{\text{passed}}}{n_{\text{total}}} & \text{otherwise}
\end{cases}
\end{equation}

where $n_{\text{passed}}$ and $n_{\text{total}}$ denote the number of passed and total test cases, respectively. Crucially, $R_{\text{task}}$ is a terminal reward computed only at the final execution step and is propagated back to all preceding turns in the trajectory (see Section~\ref{sec:traj-reward}).

\subsubsection{Interruption Cost}

Clarification may introduce interaction overhead and disrupt users who prefer efficient communication. We therefore define an interruption cost that accumulates across dialogue turns:

\begin{equation}
C_{\text{interrupt}} = \sum_{j=1}^{K} c(a_j, r_j)
\end{equation}

The per-turn cost function is defined as:

\begin{equation}
c(a_j, r_j) = \lambda - \gamma \cdot \alpha_j + \delta \cdot r_j
\end{equation}

where $\alpha_j \in \{0, 1\}$ indicates whether the user answered the clarification question and $r_j \in \{0, 1\}$ indicates whether the user rejected it. Answering a clarification question reduces the cost (encouraging informative clarification), while rejection increases the cost (penalizing unnecessary interruptions). If $a_j = \text{Execute}$, no interruption occurs and $c = 0$.

\subsubsection{Total Reward}

The reward for an interaction trajectory $\tau$ is defined as:

\begin{equation}
R(\tau) = w_{\text{task}} \cdot R_{\text{task}} - w_{\text{interrupt}} \cdot C_{\text{interrupt}}
\end{equation}

where $R_{\text{task}}$ measures the success of the final task execution and $C_{\text{interrupt}}$ captures the cumulative cost introduced by clarification. The weights $w_{\text{task}} = 1.0$ and $w_{\text{interrupt}} = 0.2$ balance task completion against interaction efficiency.

\subsubsection{Multi-turn Credit Assignment}
\label{sec:traj-reward}

For multi-turn trajectories, all turns share the final task outcome $R_{\text{task}}$ computed from the final Execute action, while interruption costs accumulate across turns. This design enables early clarification actions to receive credit if they ultimately contribute to successful task completion, while still penalizing excessive or ineffective clarification.

\subsection{Trajectory Generation with Simulated Users}

To train the clarification policy, we construct a simulation framework that generates multi-turn interactions between the assistant and synthetic users. A key advantage of this framework is its generality: it can transform any standard benchmark (e.g., BigCodeBench for coding tasks) into a multi-turn, interactive training scenario through a two-step process—masking task details to create underspecified requests, and simulating user responses to reveal information progressively. This approach enables automatic generation of diverse training trajectories from existing benchmarks without requiring human annotators or pre-existing multi-turn datasets. The framework consists of three components: task masking, user personas, and a user simulator that models interactive behavior.

\subsubsection{Task Masking and State Construction}

To create scenarios where clarification is necessary, we start with fully specified tasks from standard benchmarks and mask critical information to produce underspecified task requests. Specifically, we remove information such as input constraints, output format requirements, edge cases, and validation rules from the original task description. This masking process transforms static, single-turn benchmarks into dynamic, multi-turn interaction scenarios where the assistant must actively seek information through clarification.

For each masked task, we construct an initial dialogue state $s_1$. 
This state includes the masked task description $q_1$, an initial task uncertainty score $u_1 \in [0,1]$ computed heuristically from the masked query text (based on factors such as query length, the presence of question marks, and ambiguous keywords), the dialogue turn index $d_1 = 0$, and a reject indicator $r_1 = 0$ indicating that no clarification rejection has occurred yet. 
The query representation $q_1$ initially contains only the masked task description, and conversation history is progressively accumulated into $q_j$ as the interaction proceeds. 
The user persona $p$ is sampled according to the persona configuration.
The masked information is stored in a disclosure rule accessible only to the user simulator, which reveals parts of this hidden information when the assistant asks clarification questions, according to the persona's expertise level.

This design creates a natural information-seeking scenario in which clarification actions allow the assistant to progressively recover missing task requirements.

\subsubsection{User Personas}

To model heterogeneous user preferences in collaborative interactions, we characterize users using two interpretable parameters: \textit{patience} and \textit{expertise}. 
Patience reflects the user's tolerance for additional clarification rounds and determines the probability of answering clarification questions, which decays over dialogue turns. 
Expertise captures the user's ability to provide precise and informative answers when clarification is requested; in our design, it also determines the amount of masked information revealed per clarification round, with higher expertise enabling more efficient information disclosure.

These two parameters provide a compact abstraction of real user behavior and allow the simulator to generate a wide range of interaction styles.
Different user personas are instantiated as specific combinations of these parameters. 
For example, users with low patience may prefer rapid execution with minimal interruptions, while users with higher expertise can provide more informative responses that help the assistant resolve task ambiguity. 

In our coding experiments, we instantiate three representative personas:
\begin{itemize}
\item \textbf{Busy-Developer}: low patience and moderate expertise, prioritizing rapid execution and frequently rejecting clarification.
\item \textbf{Experienced-Engineer}: moderate patience and high expertise, answering meaningful clarification questions while rejecting redundant ones.
\item \textbf{Novice-Learner}: high patience and lower expertise, tolerant of multiple clarification rounds and willing to provide detailed explanations.
\end{itemize}
This parameterized design allows the framework to simulate diverse collaboration behaviors while remaining easily extensible to other domains and interaction settings.

\subsubsection{User Simulator}

The user simulator models how different personas respond to assistant actions. For Clarify actions, the simulator determines:

\begin{enumerate}
    \item \textbf{Answer probability}: The probability that the user answers a clarification question is:
    \begin{equation}
    P(\text{answer} | \text{Clarify}, p, t) = p_{\text{base}} \cdot (0.85)^t
    \end{equation}
    where $p_{\text{base}}$ is the base patience level of the persona and $t$ is the dialogue turn number. This models patience decay over multiple turns.
    
    \item \textbf{Reject probability}: $P(\text{reject}) = 1 - P(\text{answer})$.
    
    \item \textbf{Answer clarity}: If the user answers, the clarity of the answer is determined by the persona's expertise level:
    \begin{equation}
    c_t = \text{EXPERTISE\_MAP}[\text{expertise}]
    \end{equation}
    where expertise levels map to clarity values (low: 0.3, mid: 0.6, high: 0.9).
    
    \item \textbf{Information disclosure}: When the user answers, the simulator reveals masked task information from the disclosure rule. The amount of information disclosed per turn is determined by the persona's expertise level: low expertise reveals 1 information point per turn, moderate expertise reveals 1-2 points depending on dialogue turn, and high expertise reveals 1-2 points with earlier transitions to higher disclosure rates. This design ensures that higher expertise enables more efficient information acquisition, while lower expertise requires more clarification rounds to fully recover masked requirements.
\end{enumerate}

For Execute actions, the user provides minimal reaction (e.g., "Continue.") until the final solution is evaluated.

The simulator also implements persona-specific behaviors:
\begin{itemize}
    \item \textbf{Busy-Developer}: Rejection probability is increased to target $>80\%$ reject rate for Clarify actions.
    \item \textbf{Experienced-Engineer}: Rejects obvious or redundant questions more frequently (patience reduced by 50\% for obvious questions).
    \item \textbf{Novice-Learner}: Maintains high patience across multiple turns, rarely rejects.
\end{itemize}

\subsubsection{Multi-turn Trajectory Generation}

For each initial state $s_1$, we generate a multi-turn conversation trajectory as follows:

\begin{enumerate}
    \item \textbf{Action Selection}: At each turn $t$, select an action $a_t$ based on the current state $s_t$ and persona $p$. We use a heuristic selection function that considers:
    \begin{itemize}
        \item Task uncertainty $U_t$: Higher uncertainty increases the likelihood of Clarify.
        \item Persona patience: Lower patience increases the likelihood of Execute.
        \item Previous reject signal: If $r_{t-1} = 1$, always select Execute.
        \item Dialogue turn: Higher turn numbers increase the likelihood of Execute.
    \end{itemize}
    
    \item \textbf{Assistant Message Generation}: Generate the assistant's message $m_t$ based on the selected action:
    \begin{itemize}
        \item If $a_t = \text{Clarify}$: Generate 1-2 clarifying questions using a language model.
        \item If $a_t = \text{Execute}$: Generate a solution (e.g., code implementation) using a language model.
    \end{itemize}
    
    \item \textbf{User Reaction}: Simulate user reaction $o_t$ using the user simulator based on the persona $p$ and dialogue turn $t$.
    
    \item \textbf{State Update}: Update the state for the next turn:
    \begin{itemize}
        \item If $a_t = \text{Clarify}$ and the user answered ($\alpha_t = 1$): Update task uncertainty $U_{t+1} = U_t \cdot (1 - 0.5 \cdot c_t)$ and append conversation history to $q_{t+1}$.
        \item If $a_t = \text{Clarify}$ and the user rejected ($r_t = 1$): Set $r_{t+1} = 1$ and update $q_{t+1}$.
        \item If $a_t = \text{Execute}$: Terminate the conversation.
    \end{itemize}
    
    \item \textbf{Termination Check}: The conversation terminates when:
    \begin{itemize}
        \item The assistant selects Execute (regardless of task completion).
        \item The user rejects the assistant's action ($r_t = 1$).
        \item A maximum number of turns $K$ is reached.
    \end{itemize}
\end{enumerate}

\subsubsection{Persona-Specific Target Behaviors}

A central challenge is constructing preference pairs that teach the model \emph{distinct} behaviors for different personas. Each persona has a target interaction pattern that the model should learn:

\begin{itemize}
    \item \textbf{Busy-Developer}: Execute immediately at turn 0. Clarification is almost always unwelcome regardless of task uncertainty, because the user prioritizes speed over completeness.
    \item \textbf{Experienced-Engineer}: Clarify at turn 0 to acquire key missing information, then switch to Execute at turn 1. One round of targeted clarification is valuable, but prolonged interaction is not.
    \item \textbf{Novice-Learner}: Clarify for multiple rounds (turns 0, 1, 2, \ldots) to progressively recover missing requirements, then Execute once sufficient information has been gathered. The user's high patience makes extended clarification worthwhile.
\end{itemize}

These target behaviors yield the following ideal preference pairs at each dialogue turn:

\begin{center}
\small
\begin{tabular}{llcc}
\toprule
\textbf{Persona} & \textbf{Turn} & \textbf{Chosen} & \textbf{Rejected} \\
\midrule
Busy-Developer & $t = 0$ & Execute & Clarify \\
\midrule
Experienced-Engineer & $t = 0$ & Clarify & Execute \\
Experienced-Engineer & $t \geq 1$ & Execute & Clarify \\
\midrule
Novice-Learner & $t = 0, 1, \ldots, T{-}1$ & Clarify & Execute \\
Novice-Learner & $t = T$ & Execute & Clarify \\
\bottomrule
\end{tabular}
\end{center}

where $T$ denotes the turn at which the Novice transitions to execution (determined by remaining task uncertainty). This table defines the \emph{direction} of each preference pair: at each (persona, turn), we know which action should be preferred.

\subsubsection{Behavior-First Pair Construction}

Naively constructing preference pairs by comparing trajectory rewards leads to a fundamental conflict: since Execute trajectories directly produce task solutions, they tend to achieve higher $R_{\text{task}}$ than Clarify trajectories (where $R_{\text{task}} = 0$ for the Clarify turn itself). Under a unified reward, a purely reward-ranked approach would assign Execute as the chosen action for \emph{all} personas at turn 0, making the training signal persona-blind.

To resolve this, we adopt a \textbf{behavior-first} construction strategy. The preference direction is determined by the persona's target behavior (the table above), not by reward magnitude. Concretely, for a given (state, persona, turn), we define a target action function:
\begin{equation}
a^*(p, t) = \begin{cases}
\text{Execute} & \text{if } p = \text{Busy}, \text{ or } (p = \text{Experienced} \wedge t \geq 1) \\
\text{Clarify} & \text{otherwise}
\end{cases}
\end{equation}

The chosen trajectory $\tau^+$ is selected as the highest-reward trajectory whose action matches $a^*(p, t)$, and the rejected trajectory $\tau^-$ is the highest-reward trajectory with the opposite action. The reward is used only to rank trajectories \emph{within} each action group, not to determine the preference direction between actions:

\begin{equation}
\tau^+ = \argmax_{\tau : a_t(\tau) = a^*} R(\tau), \quad
\tau^- = \argmax_{\tau : a_t(\tau) \neq a^*} R(\tau)
\end{equation}

This design ensures that the DPO training signal directly encodes persona-aware behavioral differences. Without it, we observed that trained models exhibit identical behavior across all personas (Section~\ref{sec:experiments}).

\subsubsection{Pair Generation Pipeline}

We generate preference pairs through three complementary methods. Each method targets a different part of the persona--turn space, and together they ensure coverage of all target behaviors.

\paragraph{Method B: Turn-0 pairs and Novice multi-turn extension.}
For each (state, persona) group, we partition trajectories by their turn-0 action into a Clarify pool and an Execute pool. From each pool, we select the trajectory with the highest reward as the pool's representative. The target action $a^*(p, 0)$ then determines which representative becomes chosen and which becomes rejected, producing one pair at turn~0.

For Novice-Learner, where the chosen action at turn~0 is Clarify, we additionally trace the chosen Clarify trajectory forward through subsequent turns. At each turn $t > 0$ where the trajectory continues to Clarify, we generate an additional pair:
\begin{center}
\small
chosen = Clarify response at turn $t$, \quad rejected = Execute response from turn-0 Execute pool
\end{center}
This provides the model with multi-turn Clarify preference signals at turns $t = 1, 2, \ldots$

\paragraph{Method A: Fork-Execute pairs for Novice high turns.}
Method~B reuses the same turn-0 Execute response as the rejected example for all turns, but the dialogue state evolves across turns. To provide more accurate contrastive pairs, we fork the Novice Clarify mainline at intermediate turns: at each fork point, we branch off an Execute trajectory from the \emph{same dialogue state} as the Clarify turn. This produces pairs where both chosen (Clarify) and rejected (Execute) observe identical conversation context, making the comparison more precise.

\paragraph{Method C: Fork-Clarify pairs for Experienced turn~$\geq 1$.}
The Experienced-Engineer's target behavior requires a transition from Clarify at turn~0 to Execute at turn~1. To generate pairs for this transition, we fork the Experienced mainline at the Execute point (turn~1), generating an alternative trajectory that continues Clarifying. The resulting pair has the mainline Execute as chosen and the forked Clarify as rejected, directly encoding the turn-dependent behavioral switch.

\paragraph{Filtering rejected clarifications.}
When selecting the best Clarify trajectory as a chosen example, we exclude trajectories where the user rejected the clarification (indicated by a high interruption cost from the rejection penalty $\delta$). A rejected Clarify represents a failed interaction---the user did not engage, and the resulting reward reflects this failure. Including such trajectories as chosen examples would teach the model to prefer clarification even when it leads to user frustration. If all available Clarify trajectories for a given (state, persona, turn) were rejected, we skip that pair entirely, as there is no positive evidence that Clarify is beneficial at that point.

\paragraph{State-aligned rebalancing.}
To ensure the model sees contrastive persona signals for the same task, we retain only states where all three personas have valid preference pairs. Within each (state, persona, turn) group, we keep the pair with the highest chosen reward. This produces a balanced training set where the model can learn persona-specific behaviors from direct comparisons on shared tasks.

\subsection{Evaluation Metrics}

We evaluate the trained policy along two axes: \textbf{proactive behavior quality} (does the model adapt its clarification strategy to different personas?) and \textbf{task success} (does the generated code actually solve the problem?).

\subsubsection{Task Success Rate}

We adopt the \textbf{pass@k} metric from BigCodeBench~\cite{zhuo2024bigcodebench} as the primary measure of task success. For each task, the model generates $k$ candidate solutions. A task is considered \emph{solved} if at least one candidate passes \textbf{all} test cases associated with that task:

\begin{equation}
\text{pass@}k = \frac{1}{|T|} \sum_{i=1}^{|T|} \mathbf{1}\!\left[\exists\, j \in \{1,\dots,k\} : \texttt{score}(c_{i,j}, \mathcal{T}_i) = 1.0\right]
\end{equation}

where $T$ is the set of evaluation tasks, $c_{i,j}$ is the $j$-th candidate solution for task $i$, $\mathcal{T}_i$ is the test suite for task $i$, and $\texttt{score}(c, \mathcal{T}) = 1.0$ iff the code $c$ passes every test case in $\mathcal{T}$. This is an all-or-nothing criterion: partial test passage does not count as success. We primarily report \textbf{pass@1} as the standard task success rate.

In multi-turn evaluation, the model interacts with a simulated user across multiple dialogue turns before producing the final solution. The task success rate thus reflects the \emph{end-to-end} quality of the interaction: whether the clarification strategy (or lack thereof) ultimately led to a correct solution.

\subsubsection{Proactive Behavior Metrics}

To assess whether the model learns persona-specific clarification strategies, we measure:

\begin{itemize}
    \item \textbf{Action accuracy}: Whether the model's action (Clarify or Execute) matches the target action $a^*(p, t)$ for the given persona and dialogue turn.
    \item \textbf{Average dialogue turns}: The mean number of interaction turns before the model selects Execute. This should vary across personas (e.g., $\approx 1$ for Busy, $\approx 2$ for Experienced, $\geq 3$ for Novice).
    \item \textbf{Clarify rate}: The fraction of turns where the model selects Clarify, reflecting the overall proactivity level per persona.
\end{itemize}

The ideal outcome is a model that simultaneously achieves high task success and exhibits distinct per-persona interaction patterns, balancing task completion quality against user preference for interaction efficiency.
